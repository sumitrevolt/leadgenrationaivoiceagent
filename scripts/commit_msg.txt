fix(deploy): verify the end state, don't trust `docker compose up`'s exit code

Live incident (2026-07-14): deploy_vps.sh aborted with UP_RC=1 on

  Conflict. The container name "/0b2ef7814c97_leadgen_app" is already in use

...but production was completely fine. Docker renames the old container before
removing it during a recreate; a leftover/raced rename made compose return
non-zero while it went on to recreate everything correctly. Verified end state
after the "failure": https://leadsgenai.in/health 200, /health version c84b62a6,
and app/worker/scheduler/worker_heavy/worker_video ALL on c84b62a6 healthy.

So the script failed a deploy that had actually succeeded — and, worse, exited
BEFORE verification and retention ran. It trusted an exit code (an inference)
over the observed end state (evidence). That is the same mistake this session
already had to retract once at the analysis level; it should not be baked into
the tooling.

Now: a non-zero `up` logs a loud WARN and dumps the tail, then continues to
VERIFY. Verification decides, and it cannot pass on a genuinely broken deploy —
it requires /health.version == the deployed sha, per-container APP_VERSION match
(skew gate), and revenue/auth smoke. If verification fails, the deploy still
exits non-zero and now also reports the up code. If it passes despite a non-zero
up, the script says so explicitly rather than silently glossing over it.

This does NOT weaken the gate: the strict checks are unchanged. It moves the
verdict from "did the command exit 0" to "is production actually right".

No app code touched.
