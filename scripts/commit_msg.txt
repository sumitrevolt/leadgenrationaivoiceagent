fix(deploy): image retention — every deploy added ~7GB with no cleanup

Live finding: the VPS root disk was at 92% (178G/193G, 16G free). Each app image
is ~7.04GB and NOTHING ever reclaimed old ones, so the box was roughly two
deploys away from a disk-full outage that would take Postgres and Docker down
together. Twelve app image tags were resident; six were built today.

A one-off reclaim (unused build cache + old app tags, keeping current+rollback,
never `rmi -f`) took the disk 92% -> 61% (178G -> 118G used, 16G -> 76G free)
with prod healthy throughout and images 40 -> 31.

This closes the cause rather than the symptom: deploy_vps.sh now runs retention
AFTER a fully verified deploy (never before — a failed deploy must not also
delete rollback targets):
  - keeps the newest KEEP_IMAGES (default 3) app tags = current + rollbacks,
  - never deletes the tag it just deployed,
  - uses `docker rmi` WITHOUT -f, so docker itself refuses to remove any image a
    container still references,
  - `docker image prune -f` for untagged leftovers only; never touches volumes,
    containers, or data (no `-a`, no `system prune`),
  - prints resulting disk usage so the deploy log carries the evidence.

Build cache is deliberately left in place (~56GB, 48.89GB reclaimable via
`docker builder prune -af`): at 61% we have headroom, and the cache is what keeps
rebuilds fast. Reclaim it manually if disk climbs again.

No app code touched.
